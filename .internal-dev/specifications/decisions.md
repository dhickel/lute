# Durable Decisions

## Cache-only input listeners

- **Decision:** `KeyListener` and `MouseListener` are concrete, independently owned input caches. Managers deliver to these caches, not immediate input listener callbacks. Controllers retain their own key queues. Mouse position updates the latest cached position; selected buttons and scroll enter its queue.
- **Justification and alternative:** Deferred queue consumption preserves the existing cache-based gameplay path without a separate immediate-delivery listener API. The former callback listener implementations and cache class names are removed rather than retained as compatibility aliases; this intentionally breaks the old API.
- **Caveats:** LibGDX event callbacks and `KeyActionConsumer`/`MouseEventConsumer` queue-drain consumers remain. Consumers run when callers consume or poll, not directly from managers. Queues are bounded, so overflow can lose transitions. `releaseHeldInputs()` queues balancing releases for enabled listeners selecting each captured action; callers must drain them outside event dispatch on the main thread.
- **Affected specifications:** This decision is the current input-listener contract; `docs/input-system.md` describes its application and lifecycle.
- **Source:** User-directed input listener simplification.
- **Review timing:** Revisit if the input delivery contract changes.

## Animation-driven attack lifetime

- **Decision:** Weapon definitions use nested `stats`, `animation`, `sounds`, and `bounds` records. `stats.hit_frame` starts the attack sensor; animation completion ends the attack. Frames are zero-based: frame 0 is immediate at animation start, and frame 2 starts the third frame. `animation.speed` scales the animation clock and therefore both frame timing and total attack lifetime. The independent `attack_duration` timer and unused `hitDelay` are removed.
- **Ownership:** Player JSON supplies the base animation `frame_interval` in seconds; the equipped weapon's animation supplies its attack `frame_interval`. Both must be finite and positive. Combat passes the attack interval, animation speed, sound frame, and resolved attack-sound ID to `Animation2D` when accepting an attack. Animation emits the sound once when playback reaches or crosses `animation.sound_frame`; it does not inspect weapon definitions or manage fixtures. `EntityFactory` validates hit and sound frame limits against every facing direction when composing the entity. Animation revalidates those limits if a previously seen atlas identity is replaced. Combat reads animation progress and owns fixture creation, damage, and cleanup. An accepted attack can be active before its sensor exists. Hit sounds are loaded but not emitted.
- **Ordering and tradeoff:** The animation FSM and playback update before combat, and combat updates before physics. Accepted input configures the attack in the combat pass; its animation begins on the following update. Frame 0 is relative to that animation start. Physics retains ordinary fixed ticks with no forced contact refresh: an entire active interval skipped by an update, or shorter than a physics tick, can produce no hit.
- **Affected specifications and sources:** `assets/data/weapons.json`, `WeaponsData`, `Combat`, `CombatWeapon`, `Animation2D`, `AnimationState`, `AnimationSystem`, `CombatSystem`, `GameScreen`, and `EntityFactory`.
- **Source:** User-directed weapon asset and animation-timing refactor. This supersedes the former explicit combat-duration decision.
- **Review timing:** Revisit if attack timing, animation ownership, or physics contact guarantees change.

## Settings and weapon asset ownership

- **Decision:** `assets/game.settings.json` supplies the existing `GameConsts` values and map, data, sound, music, object, and atlas directory prefixes. `GameCore.create()` loads and validates settings before constructing runtime services or loading game data. Invalid settings fail startup without partially applying values. Static field defaults retain standalone-tool compatibility; runtime startup requires the settings file.
- **Ownership:** Map manifests declare map-owned assets. `WeaponsData` has a top-level shared `atlas` path and a `weapons` map; each weapon includes an animation atlas region key. Both atlas fields default to `NONE`. Selecting a weapon with either enabled fails explicitly until separate weapon rendering is implemented. Character animation retains the existing atlas-region naming convention and combined tutorial sprites.
- **Loading:** Only the initially equipped weapon contributes sound definitions to initial loading. Its attack and hit filenames are relative to the configured sound directory and resolve to `weapon/<weapon-id>/attack` and `weapon/<weapon-id>/hit` logical IDs. Weapon definitions do not require map sound entries. This does not add inventory, weapon switching, or automatic asset lifetime management.
- **Validation boundary:** Validate JSON, settings, and asset definitions on entry, and validate geometry and cue limits where configuration meets loaded assets. Trust validated values in runtime records and update loops rather than repeating checks. Optional state, gameplay conditions, and asset lifecycle, type, and loading failures remain meaningful checks. This keeps the closed runtime path simple without weakening external boundaries.
- **Source:** User-directed data and asset-structure refactor.
- **Affected specifications:** This decision extends the existing logical-key asset contract; `docs/asset-service.md` describes the boundaries.
- **Review timing:** Revisit when selectable weapons or separate weapon visuals are implemented.

## Custom asset service and logical keys

- **Decision:** Replace the AssetManager-backed service with a directly owning service whose logical identity is resource class and logical ID. Store entries in four typed maps selected directly by class, with a separate ordered loading `queue`. The maps alone track registered assets; diagnostics and disposal iterate them without a redundant ownership index or a cross-type insertion-order guarantee. Asset records define loads; runtime audio events and animation components carry IDs. Manifest keys remain IDs, and the manifest name is the map ID. The service supports sounds, music, atlases, and tiled maps.
- **Justification and tradeoff:** Explicit keys separate runtime identity from file paths and make ownership and unloading direct. The standalone comparison favored typed lookup in the measured workloads and showed a separate benefit from avoiding scans of loaded entries during queue updates; it does not establish a universal speedup or gameplay improvement. The complete composite implementation remains test-only for comparison. Unlike AssetManager, the service has no background loading or reference counting: queue updates synchronously load at most one entry, while an explicit load handles only its requested entry. Repeating the same key and path is idempotent; conflicting paths fail while the key exists.
- **Caveats:** Load on the render thread. Failed loads remove their entries for explicit retry; a `LoadingScreen` update failure is propagated and latched until `show()` resets the screen and queues its definitions again. Unloading cancels queued work or disposes the loaded resource; users must stop using it and its dependents first. Different keys for the same path own independent loads. Direct atlas and map loaders retain their textures until ownership transfers to the completed resource and dispose already-created textures on runtime failure; `DirectTexture` disposes its GL handle if loading fails during construction. Service disposal is idempotent.
- **Affected specifications:** This decision establishes the asset identity, loading, and ownership contract; `docs/asset-service.md` describes usage and migration.
- **Source:** User-directed replacement of AssetManager-backed asset handling; `.internal-dev/reviews/asset-storage-benchmark-comparison.md`.
- **Review timing:** Revisit if asset identity, loading, or ownership contracts change, or relevant measurement evidence changes.
