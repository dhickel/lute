# Composite Characters

## Purpose
A character consists of a base sprite and equipped head, body, hands, feet, and weapon layers. Phases 1–4 are implemented and accepted by [final integration validation](../reviews/2026-11-16-composite-character-integration.md).

## Intended Contract
### Composition and loadout
The default loadout uses the basic item in all four equipment slots and `basic_sword`. `Loadout` owns equipped equipment and the selected weapon, retaining an immutable per-entity weapon catalogue and equipment-validation callback; it does not hold `Combat`. Its constructor takes equipment, weapon ID, catalogue, and validator. `getWeapon()` returns the selected definition and `getWeaponId()` returns null for unarmed. `setEquipment` and `setWeapon` validate selections but do not guard attack state.

For guarded gameplay switches, obtain `LoadoutSystem` from the engine and call `equip(entity, equipment)` or `equipWeapon(entity, weaponId)`. It rejects a pending or active attack before validation or mutation, returning false and leaving state unchanged. Otherwise it applies the component setter. Null selects the catalogue's unarmed weapon; an unknown idle ID throws without changing the selection. `Combat` is optional for loadout changes and rendering. `Combat` owns pending and active attack state, the active attack snapshot, sensor, and hits. `CombatSystem` requires `Loadout`, selects attacks from its weapon, and cleans up active attack state and any sensor on `Loadout` removal, both before and after sensor activation. Inventory and UI are not part of this work.

Use one shared animation clock to align the facing, action, and frame of every visible layer. The compositor reads equipment and weapon from `Loadout`, without requiring `Combat`. A character without a weapon renders without the weapon layer.

### Assets
Build sprite assets from `raw_assets/sprites`: base character frames are flat in `character/`; equipment frames are organized as `equipment/<set>/<slot>/`, where slots are `head`, `body`, `hands`, and `feet`. The basic set requires all four nonempty slots. Gather sets by slot to generate separate head, body, hands, and feet atlases, preserving set prefixes in region names such as `basic/shot_up`. An optional `equipment/pack.json` supplies shared settings for these four atlases; reject nested packing overrides and unknown slots, except that `accessories` export folders are reported and skipped for now. Preserve their source files; do not pack an accessories atlas or add an equipable accessories layer. Weapons remain under `weapons/melee/basic_sword/` and `weapons/ranged/basic_bow/`. Generate separate character and common weapons atlases alongside the equipment atlases under `assets/atlases`. Sprite packing defaults to maximum page dimensions of 2048×2048. Optional `pack.json` settings inherit defaults for omitted dimensions and retain explicit overrides. Sprite pages must not mix source asset folders; reject `combineSubdirectories=true` overrides. A single folder may overflow onto multiple pages, without a guarantee that an individual animation remains on one page. Weapon region names retain their `melee` or `ranged` prefix in the common weapons atlas. With the locally provisioned inputs, character and each equipment atlas use one page, and the common weapons atlas has separate sword, bow, and arrow pages; all current eight-frame sequences remain on one page. The default arrow is `ranged/arrows/IronArrow`, sourced from `weapons/ranged/arrows/IronArrow.png`. Its sprite must remain unrotated and untrimmed, with the configured tip inside its canvas. The generator can run without this optional source, but drawing an arrow then throws a missing-region exception; there is no substitute art.

Generated runtime resources are build outputs; raw assets are the source. Both trees are local and ignored by Git. A checkout requires the complete externally provisioned raw tree and `./generate-runtime-assets.sh` before asset-dependent execution. Map-owned environmental atlases remain separate and require combined subdirectory packing. The corrected raw base and each basic equipment set have 192 frames: death, idle, jab, shot, slash, and walk, each in four directions with eight frames. Sword and bow each have 160 frames; sword has no shot, bow has no slash, and neither has cast.

### Canvas and logical bounds
Each composite character frame canvas is 128×128 pixels. The character's authored logical size is 64×64 pixels, centered at canvas coordinates [32, 96] on each axis. Render the full canvas at pixel scale, including transparent padding and overhang; do not crop it or shrink it to the logical size. Relative to the 64×64 transform, the canvas render offset is -32 pixels on each axis. Spawn placement and weapon anchors use the logical area. `logical_size` is explicitly configured, not inferred from the source canvas.

Player JSON defines `logical_size` as `{ "width": 64, "height": 64 }`, `collision_bounds` as `{ "x1": 20, "y1": 4, "x2": 44, "y2": 14 }`, and `hitbox_bounds` as `{ "x1": 16, "y1": 6, "x2": 48, "y2": 56 }`. Bounds are bottom-left-origin logical-local pixels and are converted to world units once. Both describe ellipses: the 24×10 physical feet fixture and a separate 32×50 damage-receiving hurtbox. Non-circular Box2D ellipses use the existing eight-vertex approximation. The persistent hurtbox is a sensor, not a movement blocker or map-trigger contributor. Attack sensors target it rather than solid fixtures for explicit hurtbox targets; generic full-sprite targets retain their existing fallback.

### Attacks
Space is the default primary action: a sword slash triggers on press, while holding it with a bow starts aiming and releasing the last held primary binding fires once. Keyboard, gamepad, and mouse primary actions participate; mouse position does not move the target. Shift triggers the secondary jab on press, except while aiming. Without a weapon, both keys trigger a hand jab.

Weapon `attack_stats` contains separate `primary` and `secondary` records, each with animation, bounds, stats, collision type, and its own `sounds.attack` and `sounds.hit` paths. Sound IDs are `weapon/<id>/<primary|secondary>/<attack|hit>`. Initial loading includes both sounds for every configured attack, including unarmed. Existing WAV files are approved for reuse; hit sounds are loaded but not played. A bow shot plays its animation and launches the default arrow with the primary attack's damage. The arrow follows a shallow arc toward the selected target; its swept triangular tip collides with terrain and hurtboxes, ignores its owner, and damages a living hit target. In-flight arrows are discarded when their owner or combat system is removed.

Each attack's `bounds` requires `offset_up`, `offset_down`, `offset_left`, and `offset_right`, each an object with finite, required `x` and `y` coordinates in logical-local pixels. Current authored defaults are explicitly zero in both axes; omitted or null offsets are invalid. Rotate the right-facing geometry around the logical center first, then translate by the selected facing's offset. Positive X shifts right and positive Y shifts up regardless of facing; offsets do not change the rotation pivot or shape.

Aim starts two map tiles from the player's center in the facing direction. Movement actions steer the crosshair instead of moving the player while aiming. The bow draws through shot frames 00–04 and holds 04. Releasing fires immediately once and starts frames 05–07, even on a quick release. The release pose faces the cardinal direction of the dominant target axis; vertical wins ties and a centered target preserves facing. The arrow still travels toward the exact target. Focus or input-context invalidation, death, or a weapon change cancels aim without firing. Melee attacks retain press-triggered, animation-driven hit timing and sensor lifetime. Validate authored arrow flight and tip data at loading, and validate sprite geometry against the loaded atlas when an arrow is drawn. Validate other authored data at its loading boundary and animation and geometry constraints where data meets loaded assets.

## Constraints
The composition design is reusable for future NPCs. Enemies remain full sprites with weapon variants. This work does not add NPC or enemy spawning.

There is no magic requirement. `cast` is not a runtime dependency and is absent from the corrected raw inventory.

## Decisions
Compose visible characters into distinct offscreen cells. Within each cell, draw back to front: UP uses weapon, base, feet, body, hands, head; DOWN, LEFT, and RIGHT use base, feet, body, hands, head, weapon. Omit the weapon when unarmed. Batch atlas layers across characters by their actual texture page while preserving that order. Render each completed character as one sprite, world-depth sorted with ordinary objects; do not independently world-sort its weapon or other layers. This correction changes neither weapon placement in the order nor canvas, logical geometry, or assets.

Use correct premultiplied-alpha handling so transparent edges remain correct during both composition and final rendering.

## Validation
The canvas and bounds correction is an accepted contract. Focused automated validation passed; the user's live review of the initial fitted bounds is pending. See the [canvas and hitboxes validation report](../reviews/2026-11-16-character-canvas-hitboxes-validation.md) for final gate evidence. Historical integration evidence below predates this correction and does not establish its validation.

Verify full-scale padded rendering and overhang, logical placement and anchors, separate feet and hurtbox contacts, map-trigger exclusion, missing cast, asset generation and multipage region resolution, default and switched loadouts, aligned animation in all directions, both attack keys with sword, bow, and no weapon, and bow aim, release, cancellation, projectile collision and damage. Verify overlapping characters and ordinary objects at different depths, including weapon overlap and transparent edges. Exercise resource loading and disposal. The historical final integration report records 9,917 gameplay checks, 384 framebuffer comparisons across two weapon pages, 1,402 synthetic real-GL checks, and per-attack sound selection and ID validation; its earlier check failure is not a statement about the current baseline. Bow validation reported by the implementation run includes offline asset generation and focused input, combat, lifecycle, actual-asset rendering, and project checks. For the animation revision, the implementation agent reported the isolated offline input, combat, desktop rendering and lifecycle checks passing with a stock-sword asset copy; actual-asset comparisons cover the draw and release in all directions. The user manually confirmed the original projectile feature, not the animation revision; its manual review remains pending. Physical-device testing remains unperformed.
